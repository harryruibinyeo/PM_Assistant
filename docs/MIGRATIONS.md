# Database migrations (Alembic)

Phase 4 addition. Before this, schema changes happened by hand-editing
`pmchaser/db/models.py` and relying on `init_db()`'s
`Base.metadata.create_all()` — which only creates whole tables that don't
exist yet. It has never been able to add a column to an existing table,
so every real schema change to date has needed a manual, undocumented
step against the live database. Alembic replaces that with tracked,
reviewable migration files.

## What did NOT change

`init_db()` (`pmchaser/db/base.py`) still runs exactly as before — same
`create_all()` + index creation, called from `main.py` and every test
fixture. Nothing about server startup or the test suite depends on
Alembic. Alembic is additive tooling for *future* schema changes; it does
not run automatically yet (see "Rolling this out to the live database"
below for why, and what to do about it).

## One-time setup: adopting Alembic on the live database

The live Mac database already has every table `pmchaser/db/models.py`
describes — it's been running that schema for a long time, just never
through Alembic. `pmchaser/db/migrations/versions/89799c4a02dd_initial_schema.py`
was autogenerated *from* that existing schema, so it describes what's
already there, not a change to make.

Run this **once**, against the real database, before using Alembic for
anything else:

```
cd server
PM_CHASER_DB_PATH=/path/to/the/real/pm_chaser.db .venv/bin/python -m alembic stamp head
```

`stamp head` only writes one row to a new `alembic_version` table — it
runs no `CREATE TABLE` / `ALTER TABLE` at all, so there is nothing to back
up beforehand specifically for this step (though `backup.sh` costs
nothing to run first anyway). Do **not** run `alembic upgrade head`
instead — it tries to create tables that already exist and fails loudly
(confirmed while building this: `sqlite3.OperationalError: table people
already exists`). That failure is safe (no partial writes, WAL mode logs
nothing until the whole DDL statement succeeds) — but it means an
un-stamped database, plain `upgrade head` is the wrong command.

## Adding a real schema change from here on

1. Edit `pmchaser/db/models.py`.
2. `cd server && .venv/Scripts/python.exe -m alembic revision --autogenerate -m "add whatever"`
3. **Read the generated file in `pmchaser/db/migrations/versions/`.**
   Autogenerate is a diff, not a decision-maker — it does not know your
   intent for backfilling a new `NOT NULL` column's default on existing
   rows, and it will get SQLite's very limited `ALTER TABLE` support
   subtly wrong more often than not (SQLite can't drop/reorder/retype a
   column at all without a rebuild-the-table dance, which Alembic's
   `batch_alter_table` context handles — autogenerate doesn't always reach
   for it unprompted). Treat the generated file as a draft.
4. `.venv/Scripts/python.exe -m alembic upgrade head` locally, run the
   test suite, then apply the same command to the real database the same
   way as the one-time step above (with the real `PM_CHASER_DB_PATH`).

## Why `init_db()` doesn't just call `alembic upgrade head` itself

That's the more common production pattern (migrate on boot) and is worth
doing once the one-time `stamp head` above has actually happened on the
live database — until then, wiring it into `main.py`'s startup path would
mean pulling this branch on the Mac *before* running that command crashes
the bot at boot with the same "table already exists" error, silently, on
every restart, with no chance to intervene first. Deliberately left as a
manual step for this phase; revisit once the live database is confirmed
stamped.
